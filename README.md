# WebShield IDPS

WebShield is an educational HTTP intrusion detection/prevention application. React 18, Vite and Tailwind provide the demo site and administrator dashboard. Express inspects demo requests and login submissions; detectors feed a risk engine and an IDS/IPS decision engine. Prisma stores users, traffic, threats, rules, blocks, labels and test reports in SQLite. Socket.IO delivers live events to authenticated administrators.

This is application-level HTTP inspection, not a packet sniffer, operating-system firewall, or production WAF. There are no AI/ML services, external APIs, Docker files or cloud services required.

## Requirements

- Node.js 20 or newer (verified with Node 24.11.1 and npm 11.6.2)
- A writable project directory
- A browser

## Clean local setup

Run these commands from the project root in PowerShell:

```powershell
npm ci
Copy-Item server/.env.example server/.env
```

**If `server/.env` already exists, edit it instead of overwriting it.** Set `JWT_SECRET` to your own private value of at least 32 characters. Set `ADMIN_PASSWORD` and `USER_PASSWORD` before the first seed. No deployment secrets are bundled or generated by setup.

```powershell
npm run db:generate
npm run db:deploy
npm run db:seed
npm run build
npm start
```

Open http://localhost:3000 and sign in using the account you configured. Production mode serves the React build and API from the same origin. `npm run db:deploy` creates a missing SQLite file before applying existing migrations, without resetting an existing database. Repeating the seed preserves existing passwords, roles, rule switches and mode; it updates built-in rule score metadata.

For development after database setup:

```powershell
npm run dev
```

Open http://localhost:5173. Vite proxies `/api` and `/socket.io` to the backend on the `PORT` configured in `server/.env` (3000 by default). No frontend environment variables or API credentials are required.

Stop the servers with Ctrl+C. Do not run production and development backends on the same port at the same time.

## Environment variables

These belong in `server/.env`:

```dotenv
NODE_ENV=development
PORT=3000
HOST=0.0.0.0
JWT_SECRET=
COOKIE_SECURE=false
ADMIN_EMAIL=admin@webshield.local
ADMIN_PASSWORD=
USER_EMAIL=user@webshield.local
USER_PASSWORD=
DATABASE_URL="file:./dev.db"
TRUSTED_PROXY=false
CORS_ORIGINS=
```

- `JWT_SECRET`: required private signing value, at least 32 characters. Blank/example values are rejected. Never put this in frontend code.
- `DATABASE_URL`: SQLite URL, relative to `server/prisma`, not the shell directory.
- `ADMIN_PASSWORD`, `USER_PASSWORD`: required by the seed; choose private passwords. Email values identify the accounts to create. Re-seeding does not reset existing accounts.
- `PORT`, `HOST`: optional listen settings. Use `127.0.0.1` for local-only access or `0.0.0.0` for the LAN demonstration.
- `COOKIE_SECURE`: set `true` with HTTPS; use `false` for the local HTTP demo.
- `TRUSTED_PROXY`: leave `false` for direct LAN access. Behind a reverse proxy, provide exact trusted IPs/subnets, comma-separated, such as `127.0.0.1`. `true` is rejected because it trusts arbitrary forwarded addresses. Configure the proxy to overwrite forwarding headers.
- `CORS_ORIGINS`: optional exact comma-separated origins for a separately hosted frontend. Empty is appropriate for both bundled production serving and Vite's proxy. Cookies use SameSite=Strict, so unrelated cross-site frontend deployments need a separate design.
- `NODE_ENV`: development by default; `npm start` explicitly sets production.
- `TEST_DATABASE_URL` is no longer used. Tests create fresh disposable SQLite databases and fixed test-only accounts without reading deployment passwords.

## Routes and authorization

- `/api/auth`: registration, login/logout, current user and socket access token.
- `/api/demo`: authenticated profile/dashboard and protected data; public search/contact/test traffic endpoints.
- `/api/admin`: administrator-only overview, logs, analytics, rules, mode, labels and block management.
- `/api/test-lab`: administrator-only test definitions, lifecycle, evidence submission and cleanup.
- `/health`: tests database connectivity and returns 200 or 503.
- `/api/public`: intentionally uninspected public diagnostic endpoint.

Passwords are bcrypt hashes. Sessions use HTTP-only JWT cookies; protected APIs re-check the user's current database role. Frontend route guards keep anonymous/regular users out of the admin UI. Authenticated management routes remain available if IPS blocks the administrator's source IP, allowing recovery without bypassing API authorization. Demo traffic and login/registration requests remain inspected.

## IDS and IPS demonstration

1. Log in as an administrator and select IDS in Settings.
2. Send a normal request to `/api/demo/public`.
3. Send the following SQL injection or XSS probe to the local demonstration server:

```powershell
curl.exe -G http://localhost:3000/api/demo/search --data-urlencode "query=' OR '1'='1" -A "Mozilla/5.0" -i
curl.exe -G http://localhost:3000/api/demo/search --data-urlencode "query=<script>alert(1)</script>" -A "Mozilla/5.0" -i
```

IDS allows these requests and records threat events. IPS blocks the SQL injection (score 40) and XSS (score 45) requests with HTTP 403 and a temporary source block. Unblock the source in Blocked Sources between independent probes. Existing active source blocks are honored in every mode. MONITOR still inspects and logs but creates no new prevention actions.

For a three-computer LAN demo, connect the computers to the same private network, bind the server to `0.0.0.0`, and use the host's actual LAN IP instead of localhost. Permit the configured TCP port only on the appropriate private Windows Firewall profile. Verify access from each physical client; local automated tests cannot prove LAN/firewall connectivity.

## Test Lab

Tests send genuine HTTP requests, record response request IDs, and correlate them with persisted traffic/security evidence. Run identifiers require an administrator session or an expiring run-scoped proof. Cleanup only removes blocks owned by the run and resets detector counters between probes.

Provide a test-user email/password in the optional Test Lab fields to exercise real login without replacing the administrator's cookie. Browsers control User-Agent, so that probe is explicitly **unavailable** in the browser report. Missing credentials, network errors and missing correlations remain visible instead of being dropped. The Node integration suite exercises User-Agent detection with a real HTTP client.

Rate-test requests below the documented 50-request threshold are expected normal traffic. Repeated login tests expect basic authentication failure events before the five-failure abuse threshold. All individual observations remain in the report. Run probes sequentially from a dedicated client: unrelated traffic from the same IP can legitimately affect behavioral detector results.

Search returns intentionally illustrative demo results. Contact only acknowledges a request; it does not send email. Demo dashboard counters reflect traffic from the current source IP.

## Verification

```powershell
npm test
npm run test:integration --workspace server
npm run lint
npm run build
npm run test:watch
```

The default suite runs four existing unit scripts and all integration scripts, including API validation, access control, block recovery/ownership, rule persistence, database isolation, real-time Socket.IO delivery, and full IDS/IPS lab workflows. Tests preserve the configured application database; temporary test databases are under `server/prisma/test-run-*` and are ignored by Git. No separate database service is needed.

`npm run db:reset` is destructive; it is not part of setup or verification. Use migrations and the UI for normal operation.
